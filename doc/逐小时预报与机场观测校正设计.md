# Weather99：逐小时预报 × ZSPD METAR × 和风实时修正

> 2026-11-18 | 状态：**Shadow v1 已实现，交易逻辑未切换**。算法为 weather99 自主研究，不是 FMZ 680665 的公开源码，也不是已验证的预测能力。

## 1. 要预测的到底是什么

Polymarket 上海温度市场的目标是按**当期市场原文结算规则**定义的 ZSPD 最高温度档，不是“上海市区平均气温”或 Open-Meteo 网格最高温。

已经接入的天气源各司其职：

| 来源 | weather99 的已有数据 | 角色 |
| --- | --- | --- |
| Open-Meteo ECMWF IFS 0.25° | 每日最高温、逐小时 temperature_2m | 未来温度曲线 |
| Open-Meteo GFS Global | 每日最高温、逐小时 temperature_2m | 未来温度曲线 |
| Open-Meteo CMA GRAPES Global | 每日最高温、逐小时 temperature_2m | 未来温度曲线 |
| Open-Meteo JMA Seamless | 每日最高温、逐小时 temperature_2m | 未来温度曲线 |
| AviationWeather ZSPD 常规 METAR | 原始报文、精确 RMK T 温度、时间戳 | 机场观测、已实现最高温、规则核验 |
| 和风当前天气 5 点 | 中心与四周网格温度、validTime | 局地趋势及时间对齐后的辅助偏差 |
| 和风每日预报 | 机场中心网格 3 天 Tmin/Tmax | 单独 Challenger，不参与默认融合 |
| Polymarket Gamma/CLOB | 结算规则、温度档、盘口和最终 resolved | 价格与结算事实，不用来污染气象预测 |

**小时序列与小时更新频率不同。** 部分原始数值模型输出间隔比一小时更粗，Open-Meteo 可以插值展示逐小时数据。轮询 API 不等于模型刚发布新运行版本。必须保存 model_run/issued/available_at；拿不到原始发布时间就显示未知，不把 fetched_at 冒充模型起报时间。和风五个空间点属于同一数据源，不能视为五个独立模型。

## 2. 两条隔离的计算链路

现有 Paper 的 `equal_weight_baseline` / `trained` 模型、`intraday_residual_v1`、`normal_integer_rounding`、`strategy.evaluate`、`paper_ledger` 全部保持原样，避免未经验证的参数直接改变持仓。

新 Shadow 只做逐小时曲线和最终最高温的**诊断性点预测**；每次 `process_capture()` 在已有快照成功核验后生成 `hourly_shadow`，随本轮 `paper_cycles` 一起存入 SQLite，通过 dashboard 的 `scans[].hourly_shadow` 只读展示。Shadow 中 `trade_eligible=false`，不会进入交易风控、确认计数或建仓。

新代码：`weather99/hourly_nowcast.py`；测试：`tests/test_hourly_shadow.py`。

## 3. Shadow v1 公式（明确是未验证假设）

在北京时间的当前决策时刻 `t0`，对于四模型同一小时曲线 `M_m(t)`：

```
M(t) = 四模型小时温度的算术平均
r_METAR = ZSPD 的当前常规 METAR 温度 - M(该观测时间)
r_Q     = 和风五点同时刻网格均温 - M(和风有效时间)

有当日、新鲜且时间对齐的 ZSPD METAR 才能做小时修正
和风有效条件：5 点齐全、同 validTime、更新不超过 60 分钟、
              与 METAR 的有效时刻相差不超过 30 分钟、
              两者温度残差差异不超过 2°C
若和风无效：r = r_METAR
若和风有效：r = 0.75*r_METAR + 0.25*r_Q

初始修正 delta0 = clip(0.5*r, -2°C, 2°C)
未来 h 小时的修正 = delta0 * 2 ** (-h/3)
```

为将当前日最高温校准中心与小时模型路径对齐，先计算四模型各自在全日小时曲线上的最高温，再取四模型均值 `D_hourly`，定义 `a = baseline.center_c - D_hourly`。这属于 **hourly-to-daily calibration alignment**，不是把已经修正过的 Paper 日内中心再加一遍。每模型未来小时修正为 `M'_m(t) = M_m(t) + a + delta(h)`。

定义：`H = max(截至此刻的有效 ZSPD 常规 METAR 温度)`；`R = mean_m(max_{t>t0} M'_m(t))`。Shadow 的最终最高温参考点预测：

```
Tmax_shadow = max(H, R)
```

这是一个点预测，**不是可用于交易的已校准整数档概率分布**。时间衰减半衰期 3 小时、0.75/0.25 权重、0.5 增益、2°C 限幅，均是研究假设；需用历史真实预报 vintage 与站点日内观测学习或淘汰。

## 4. 明确排除的捷径

- 不把 5 个和风网格点当 5 个独立观测或独立 NWP。
- 不因和风“更快”就覆盖机场 METAR 的最高温/正式结算口径。
- 不把 Open-Meteo 当前查到的历史预报当作当时已发布的预报。
- 不把高频重复采集的同一 validTime 当作新增独立数据。
- 不把 Shadow 的点温度硬塞进原有固定 sigma，伪造新概率。
- 不采用将正态 X 条件化为 X>=H 的“截断再归一化”作为日内最高温通用规则；未来概率引擎应对每条随机**剩余温度轨迹**计算 `max(H, future_max)`。
- 不从市价中反向调整气象预报再将其拿来证明对市场存在独立信息优势。

## 5. 下一阶段算法：小时联合误差场景

先补齐每个模型的 `model_run_at`、`available_at`、`valid_at`、当地时间层、METAR `receiptTime` 以及真实结算结果的历史样本。按观测时点及剩余时间构建误差轨迹 `epsilon_m(t)`，保留同一模型相邻小时误差的相关性，不能把不同小时当独立白噪声。

每条样本轨迹 `j`：`H_j = max(observed_max, max_{future t} corrected_m(t)+epsilon_j(t))`，然后按市场当前结算规则映射成整数温度桶概率。校准维度至少包括 24h/12h/6h/3h、当天当地小时、已观测最高温接近预计峰值的程度，以及来源可用性。

用严格历史逐时 walk-forward，比较：
1. A0：当前 Paper 等权固定 sigma + 旧 nowcast；
2. A1：等权固定 sigma，无旧 nowcast，评估其真实增量；
3. B：各模型历史 bias + 约束权重 + 经验误差；
4. C：B + 本文件的 METAR/和风逐小时 Shadow 校正。

对照应共同使用同一份输入、结算事实及真实盘口，分别统计 Tmax MAE、整数档 Brier/LogLoss/RPS、概率覆盖率、相对市场的样本外增量和假设成交净 PnL。若无可用 vintage，显示“不足以验证”，而不是声称优于基线。

## 6. 验收和运行

```bash
python -m pip install -e .
python -m unittest discover -s tests -v
python -m weather99 paper run
python -m weather99 web --port 8765
```

检查 `runtime/paper/paper.sqlite3` 中 `paper_cycles.payload.hourly_shadow`，及页面“METAR × 和风”下面的 **逐小时最高温 Shadow（不参与下单）**：查看观测下界、剩余小时峰值、修正最终最高温、每个小时原始均温与修正均温。

必须通过的回归条件：未来样本不参与校正；只有 METAR 合格才有 Shadow；和风缺失或偏离机场时自动排除；四模型未来任一小时缺失则无预测；观测到的最高温永远不下降；旧 Paper/结算路径行为不变。以上均为逻辑与单元测试验证，不代表已经完成真实市场的概率校准。
